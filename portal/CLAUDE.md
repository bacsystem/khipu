# portal/CLAUDE.md

Guidance for the Next.js portal. Claude Code loads it when a file under `portal/` is opened; the repo-wide rules (GitFlow, `/pr-review`, `gh stack`, agent team, secrets) live in the root `CLAUDE.md`.

## Commands

```bash
cd portal
npm run dev                                        # http://localhost:3000, needs API_BASE_URL (default http://localhost:8001)
npm run build                                       # do not run concurrently with `dev` against the same .next/ — corrupts the dev server
npm run test                                        # Vitest
npx vitest run src/lib/session.test.ts              # single test file
npm run e2e                                         # Playwright; auto-starts its own dev server on :3100 with mocked backend (see below)
npx playwright test e2e/login.spec.ts               # single spec
npm run lint
npm run generate:api                                # regenerate src/lib/api/openapi.d.ts from a running backend's /openapi.json (API_BASE_URL, default http://localhost:8001); see the contract guard below
npm run typecheck                                   # tsc --noEmit
```

## Architecture

### BFF pattern over the same API

Next.js App Router (`portal/src/app`). The browser never receives the JWT:

- `src/app/api/auth/*` route handlers call the Java API server-side and set `khipu_access`/`khipu_refresh`/`khipu_empresa` as `httpOnly` cookies (`src/lib/session.ts`).
- `src/app/api/proxy/[...path]/route.ts` forwards any other `/v1/**` call, attaching `Authorization`/`X-Empresa` from cookies, and retries once on 401 by refreshing (a module-level single-flight guard, `refrescarUnaVez`, avoids two concurrent requests both rotating/invalidating the same refresh token — see the route's own comment for why).
- `middleware.ts` (edge runtime) proactively refreshes an expired access token (decoding its `exp` client-side via `src/lib/jwt.ts`, no signature check — the backend is the actual authority) before Server Components render, since Server Components hit the backend directly with `src/lib/api/*.ts` (not through the proxy) and have no way to react to a 401 mid-render.
- `src/lib/api/*.ts` are hand-written, snake_case-typed clients matching the API's actual runtime JSON shape, and **they stay hand-written on purpose**: springdoc marks no field as required (everything comes out `campo?: T` in the generated types) while the JSON does carry them and omits null keys, so generated types would force `!` and checks everywhere and say less. What the generated file is for is a **contract guard**: `src/lib/api/openapi.json` (the API's OpenAPI, committed) and `openapi.d.ts` (generated from it) are compared with the hand-written types by `src/lib/api/contrato-openapi.ts`, a types-only file where `tsc` (`npm run typecheck` and the commit hook, not eslint) fails if the backend renames or removes a field the portal uses, changes its shape, adds a value to an enum the portal lists, or (request bodies) adds a required field the portal does not send, naming the key path. `DeveloperPortalE2ETest` fails when the committed `openapi.json` is not what the running API serves, so a backend change that moves the contract cannot merge without regenerating it: `API_BASE_URL=http://localhost:8001 npm run generate:api` (JSON and types; the backend must run with `OPENAPI_RUTAS_OCULTAS=` empty, as `docker-compose.yml` does, because its default hides `/v1/admin/**` from the published spec (#602) and the script refuses a spec without them; `npm run generate:types` redoes only the types from the committed JSON), then fix what `typecheck` flags. See `contrato.ts` for what is compared, its known limits and its own tests (they compile counter-examples), and add a pair to `contrato-openapi.ts` for every hand-written type that models an API response or request body. springdoc names schemas by the class's simple name, so two nested records with the same name (an `ItemDto` in the request and another in the response) collapse into one schema and the docs lie about one of them: `NombresDeEsquemasOpenApiTest` fails on a repeat, and the fix is `@Schema(name = "…")` on one of them.
- UI text (#25): every user-visible string lives in `src/messages/es.json` (source) and `en.json`, read through next-intl 4 **without locale routing** (locale from the `khipu_locale` cookie in `src/i18n/request.ts`, default `es`; no `/en/...` URLs, `middleware.ts` untouched). Components use `useMessages()` / `await getMessages()` as a typed object, `lib/` helpers take `messages: Mensajes` as a parameter, `lib/formato.ts` takes the locale. `npm run lint` enforces it with `khipu/no-literal-de-ui` plus the `eslint-suppressions.json` baseline, which may only shrink (prune it after migrating; never `--suppress-all` a new literal). Details and test helpers in `portal/README.md`, «Textos e idiomas».
- Test mocking: `src/mocks/` (MSW) is wired in via `src/instrumentation.ts` (with a `src/` dir Next only picks it up there: at the portal root it was silently left out of the build), active only when `API_MOCKING=enabled` (set by `playwright.config.ts`'s `webServer.env`) — Playwright e2e runs against a fully in-memory fake of the auth/empresas/series/facturas endpoints, not a live backend.

### Components come from the design system package

The generic components are **not** in the portal: they come from the `khipu-design-system` package (repo `bacsystem/khipu-design-system`, pinned by tag in `portal/package.json`, e.g. `github:bacsystem/khipu-design-system#v0.5.7`). Import them from the package — `khipu-design-system/ui/button`, `/ui/dialog`, `/ui/table`, `/feedback/alerta`, `/formularios/campo`, `/navegacion/tabs`, `/patrones/pie-tabla`, `/patrones/boton-copiar`, `/nav/theme-toggle`, `/lib/paginacion`… — never re-create a copy under `src/components/` (there is no `components/ui/` any more).

- **Fix it in the DS first, then bump the tag.** A change to a shared component, a recipe or a token goes to the DS repo, gets released as a new tag, and reaches the portal by changing the version in `package.json` (`npm install github:bacsystem/khipu-design-system#vX.Y.Z`). `npm install`/`npm ci` fetch the tarball over HTTPS and run the package's `prepare` (builds `dist/`); no `git` needed, which is what the `node:22-alpine` Dockerfile relies on.
- `src/lib/estilos.ts` is a facade (`export * from "khipu-design-system/lib/estilos"`), so code keeps importing recipes from `@/lib/estilos`; `src/lib/utils.ts` re-exports the DS's `cn` (`khipu-design-system/utils`), which knows the named type scale: the generic `cn` takes `text-control` or `text-etiqueta` for a text color and erases the size or the color next to another one (`utils.test.ts`). Text sizes are the DS's named scale (`text-etiqueta`, `text-control`, `text-cuerpo`, `text-titulo`, `text-titulo-pagina`, `text-metrica`); `tipografia.test.ts` fails on a loose size, a Tailwind size, `uppercase` or wide tracking outside the landing, the legal document and the developers' guide. `alturas.test.ts` checks the imported recipe values (every control `h-control`, 32 px since v0.5.3; a hand-written `h-9` next to a control is a finding) and scans only the portal's own `src/`. Tables follow the DS pattern (§12): `CONTENEDOR_TABLA`, a header row with no band (`hover:bg-transparent`), no row borders or hover of their own (the DS cells draw the rounded bands), and `FilaVacia` for empty/loading rows; `tablas.test.ts` fails otherwise. A metric whose value is a word passes `texto` to `compartidos/metrica` (18 px instead of 22).
- `src/app/globals.css` imports `khipu-design-system/styles.css` (tw-animate-css, shadcn variants, `dark` variant, theme, base layer, `@source` of the package) and nothing else but two `--color-code*` aliases and the hero's `khipu-anillo` keyframes: since v0.5.0 the portal wears the DS theme as it is (palette Lima, dark tone Medianoche, Inter + JetBrains Mono, 32 px pill controls (since v0.5.3), a 248 px sidebar; icons are Phosphor like the DS's: client components import from `@phosphor-icons/react`, server components from `@phosphor-icons/react/dist/ssr` with an explicit weight (`PESO_ICONO`), because the main entry builds a React context and breaks in a server component; `iconos.test.ts` fails on a `lucide-react` import or a functional icon without its bold weight), and the palette, dark tone and font are the user's choice in the DS's `Apariencia`. Do **not** declare a `:root` or `.dark` there — a lone `:root { --primary: … }` after the import would override the chosen palette and, with the same specificity as the DS's `.dark`, dark mode (`tema-del-paquete.test.ts` guards it). `layout.tsx` puts `ScriptDiseno` in `<head>` (no flash of the wrong theme) and `providers.tsx` wraps the DS's `Providers`. A date field is the DS's `EntradaFecha` (a button that opens a calendar, not an `<input type="date">`): tests drive it with `src/test/fecha-de-prueba.ts`. A combo is the DS's too (#555): `SelectCampo` (`formularios/select-campo`) in a form, `Combobox` for a long catalog one types to search, the `Select` pill (`CONTROL_FILTRO`) in a filter bar — never a native `<select>` (`combos.test.ts` fails on one or on the deprecated `SELECT_NATIVO`); tests drive it with `src/test/select-de-prueba.ts` (`elegirOpcion`, `opcionesDe`) and `e2e/combo.ts`.
- **The app shell is the DS's** (#505): `(privado)/layout.tsx` is `khipu-design-system/nav/shell` (floating sidebar card, borderless top bar), and the sidebar, its nav, the logo, the company selector, the mobile drawer and the top bar are `nav/sidebar`, `nav/sidebar-nav`, `nav/logo`, `nav/selector-contexto`, `nav/mobile-nav` and `nav/top-bar`. The portal only fills their slots: `components/nav/grupos-de-navegacion.ts` (translated groups, filtered by role), `sidebar-content.tsx`, `empresa-selector.tsx` (the `seleccionarEmpresa` action), `top-bar.tsx` (translated breadcrumb, environment pill, the page's actions) and `logo.tsx` (name, domain and glyph). The landmark names are translated and passed as props (`etiquetaMenu`, `etiquetaUbicacion`, the drawer's `etiqueta`; `nav.principal`, `nav.ubicacion`, `nav.abrirMenu`). Vitest inlines `khipu-design-system` (`vitest.config.mts`) so that a test's `vi.mock("next/navigation")` reaches the DS nav components. The DS drawer scrolls since v0.5.2 (`menu-movil.spec.ts` guards that the user menu stays reachable on a short screen). The backoffice (`app/admin/(panel)/layout.tsx`) uses the same `Shell`, `SidebarContent` and `MobileNav` (`components/admin/admin-sidebar.tsx`, groups from `seccionesAdmin`, «Inicio» `/admin` marked `exacto`), but keeps its own `admin-top-bar.tsx`: its breadcrumb is not the page's `h1`.
- What stays in the portal on purpose: `components/compartidos/` (`Metrica`, `ReferenciaTecnica`), `components/forms/form-field` (react-hook-form), `components/formularios/buscador-con-lista`, the user menu (`nav/perfil-usuario`: translated, role, change password, «Apariencia…» that opens the DS's `PanelApariencia`) and the plan card (`nav/plan-y-consumo`), `providers.tsx` and `lib/formato`.
